You are here because a test you expected to pass failed, a build/test/run command exited non-zero, a traceback appeared, run output contradicted your prediction, or the user reported a bug you have not reproduced this session.

Full playbook: invoke `superpowers:systematic-debugging` via the Skill tool — it owns the fuller reproduce → hypothesis → fix loop. Not loaded this session? Follow the anchors below.

- D1. Reproduce FIRST: run the exact reproduction command; paste its failing output and quote the line showing the REPORTED symptom. The bug is fixed ONLY when that same command, unmodified, re-runs and passes — paste that too. Cannot reproduce -> `CANNOT-REPRODUCE: <commands -> outputs>` and ask; never fix blind.
- D2. "Worked before / stopped working": re-verify the ENVIRONMENT before touching code — server up (`lsof -ti :PORT`), right branch (`git branch --show-current`), package installed (`pip show <X>`), artifact rebuilt after the edit. Any belief last verified >15 messages ago (or before a compaction) is stale. (Referenced by .claude/docs/guardrails/SESSION.md.)
- D3. CAUSE line before any fix: `CAUSE: <file:line where the bad state originates> -> <propagation path> -> SYMPTOM: <file:line where it surfaces>`. Your edit targets the CAUSE end; a symptom patch is labelled `WORKAROUND: <why the root cause is out of reach>`.
- D5. Never re-run a failing command unchanged — state the hypothesis and what changed first. Suspected flake -> run 3x isolated, paste all 3.
- D6. Failed-attempts ledger: after EVERY failed fix, BEFORE retrying, append `ATTEMPT n: <what changed> -> <exact observed failure>` (to the task widget, or .claude/docs/guardrails/STATE.md `## Failed attempts` if the task spans a compaction). A next attempt differing only in surface details is forbidden -> change something structural. (Referenced by .claude/docs/guardrails/SESSION.md S3.)
- D10. About to weaken a failing check to get green? Quote the failure, propose the change, wait for approval — a silenced check certifies the regression. (In athena this is a `CLAUDE.md` `## Hard stops` violation; a repo that kept its own CLAUDE.md may have no such section, and the rule binds anyway.)
- D11. 2 hypotheses falsified in a row (D6 ledger): change the CLASS of evidence — different tool, layer, or representation, and ask the refusing component for its own diagnostics (7 static theories fell to one `CUDA_LOG_FILE=stderr`). Scope: rotation is per-hypothesis; D6's structural-change rule is per-attempt; the attempt count never resets down — attempt 5 is revert-to-a-named-ref, and there is no attempt 6.
- D12. Diagnostics gathered outside the failing runner's environment are NOISE — reproduce under the runner's exact env (container, interpreter, cwd) before theorizing (host-vs-container diverges silently).
- D13. Before declaring the environment broken: check the breakage is not self-inflicted this session — your own earlier export, kill, or tmp-write (`history`-check beats re-provisioning). This includes CONCURRENCY YOU STARTED: any build or suite still running reads the SAME live tree, so it sees your uncommitted edits and its red is evidence about you, not the code. Run ONE probe at a time. (athena §622: a background pytest run surfaces uncommitted control-neuters as failures, and two runs share one Postgres — a `finally: DROP TABLE` in one blanks the other's fixture mid-assertion. Your repo's version of this is its own; the rule is not.)
- D15. A test named in a FAILURE line is not automatically the thing that failed. Before debugging it, confirm the runner reported an ASSERTION and not a worker/process death: capture full output and `grep -E "node down|crashed while running|^E "`. No `E` line = the named test is a casualty. (athena: `docs/reference/environment.md` under `docker-test-serial` has the worked example + the two known families — that path is athena-only — §2001 retired the last `eugo:` slots, so an `(athena: …)` label is now the ONLY form a repo-specific example takes in this kit.)
- D14. A derived artifact (report, generated file, parsed log) comes out empty or wrong: Read the DERIVER/parser first, then the data (a skipped parser read cost 2 runs and 1 false rule).
